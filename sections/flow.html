一次压缩，逐步走：Hippo 到底多做了什么

40 轮合成对话共 81 条消息（含 8 条注入的精确事实），跑一次真实的压缩。上游把「摘要桶」里的消息全部换成摘要文本；Hippo 在换之前先给桶里每条消息打一个分，把分数最高、且能塞进硬预算的几条原样留在上下文里。下面五步就是这一次压缩的逐步回放。

页面上的每个数字都来自 sections/flow.json——它由 benchmarks/demo/exportFlow.ts 调用本仓库真实的 CompactionEngine 与 EbbinghausPageRankPolicy 生成，用假模型出摘要（固定字符串），不联网、不用 API key、不调真 LLM。同一 seed 重跑两次输出逐字节一致。这不是一次实时模型调用，是一次可离线复现的固定种子回放。

1压缩前 81 条消息 · 4200 tokens

进上下文前先看原样：40 个 user/assistant 来回，加最后那条待回答的请求（第 81 条）。最后一条请求是打分用的查询 q。

静态摘要（JS 未运行 / flow.json 未加载）
  • 81 条消息 = 40 组 user/assistant 对话 + 1 条待回答的请求；压缩前共 4200 tokens。
  • 其中 8 条 user 消息带注入事实（FACT1…FACT8），分别在第 1、7、15、23、31、37、45、53 条。
  • 第 81 条 Answer the TCGA-LIHC n/frequency/statistic questions… 是这次压缩要服务的请求，也是打分用的查询。
  • 此时还没有任何消息被摘要，也没有任何消息被逐字保留。
2进入摘要桶的候选 60 条候选 · 尾部 21 条不动

压缩先把对话切成「尾部」和「前缀」：尾部按 token 预算逐字保留，前缀整体进摘要桶——桶里的消息原话就没了。这次尾部 = 最后 21 条（第 61–81 条，含待回答的请求），不参与打分；剩下 60 条是候选，也就是这张图里被标黄的那些。

静态摘要
  • 尾部预算 = floor(4200 × 0.18) = 756 tokens，实际取到最后 21 条逐字保留，不参与打分。
  • 前缀 60 条进入摘要桶，成为候选——上游在这里就把它们全部换成摘要文本。
  • 8 条 FACT 消息全部落在候选里（第 1…53 条），所以上游压缩后一条原文都留不下。
  • 待回答的请求在尾部，因此不会被摘要掉。
3打分：本地算，不花第二次模型调用 60 条候选 · 权重 0.85 / 0.15 / 0.00

Hippo 给每条候选单独打分：S(m) = 0.85·sim(q,m) + 0.15·position_decay(m) + 0.00·idf_pagerank(m)。sim 是查询与消息文本的 BM25 词面相似度，position_decay 是按「越新越靠前」的指数衰减，idf_pagerank 是实体图中心度（本版权重为 0，只作显示）。三项都在进程内算完：没有第二次 LLM 调用，没有网络。下面按分数从高到低排。

静态摘要
  • 公式：S = 0.85·sim + 0.15·position_decay + 0.00·idf_pagerank，查询是最后那条请求。
  • 分数最高的 8 条恰好就是 8 条 FACT 消息：0.8986 / 0.8817 / 0.8669 / 0.8571 / 0.8455 / 0.8353 / 0.8264 / 0.8205。
  • 其余 52 条候选最高只有 0.7164，最低 0.0581——差距主要来自 sim（FACT 消息 sim≈0.9004，噪声消息约 0.67 及以下）。
  • 全部计算在本地完成：BM25 词频统计 + 指数位置衰减 + 实体图 PageRank，不调用模型。
4预算截断 硬预算 256 tokens

逐字保留是有硬预算的：max(256, floor(756 × 0.2)) = 256 tokens。按分数从高到低往下取，取到装不下为止。注意实现细节：装不下的一条会被跳过，然后继续往下试更小的消息——不是一撞到上限就停。这次 6 条刚好用掉 226/256，第 7、8 名（就是 FACT1、FACT2）无论放哪都超预算，于是留在摘要桶里。

静态摘要
  • 预算 max(256, floor(756 × 0.2)) = 256 tokens（756 是尾部预算，0.2 是保留比例，256 是下限）。
  • 按分数顺序取：36 + 37 + 40 + 38 + 38 + 37 = 226 tokens，共 6 条，落在上限 256 以内。
  • 第 7 条（FACT1，37 tokens）会让累计到 263，第 8 条（FACT2，39 tokens）会到 265，都超过 256，所以跳过。
  • 60 条候选里 6 条被逐字保留，其余 54 条留在摘要桶里（跳过而非截断，剩余 30 tokens 装不下任何一条）。
5结果：两栏对比 上游 1253 tokens · Hippo 1479 tokens

左边是上游压缩后的上下文，右边是 Hippo 的。两栏的摘要文本完全一样（同一次假模型输出），差别只在右栏多了 6 条逐字保留的原文——就是 FACT3…FACT8。上游那条请求现在只能问摘要里的东西，Hippo 还能查到原文。

静态摘要
  • 上游压缩后 1253 tokens，0/8 条 FACT 原文存活；Hippo 压缩后 1479 tokens（多出的 226 正好是保留的原文），6/8 条 FACT 存活。
  • 存活的是第 15、23、31、37、45、53 条消息，即 FACT3…FACT8；FACT1、FACT2 因为排在第 7、8 名、装不进 256 token 预算而只留在摘要里。
  • 两栏的摘要文本相同（都是固定的假模型输出），差别只是右栏多了 6 条原文块。
  • Hippo 侧的边界标记里写着 messagesSummarized="54"：被逐字保留的 6 条是从摘要桶里拿掉的，改为原样回放，送去写摘要的是剩下的 54 条——与上一步的截断结果一致（上游侧没有保留机制，标记里是完整的 60）。
