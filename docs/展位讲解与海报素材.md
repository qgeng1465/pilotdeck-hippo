> 方向三 · 硬核极客（改进 PilotDeck 底层 Harness / Memory）
> 配套数据全部可复现：`pnpm benchmark` / `benchmark:ablation` / `benchmark:tune` / `benchmark:real-llm`

## 一、30 秒电梯陈述（评委刚走近时）

"上游 PilotDeck 压缩上下文时，把历史一刀切成一段摘要——精确数字、文件路径、检查点全部有损。我们给 CompactionEngine 加了一层**评分式选择性保留**：把将被摘要的消息按「语义相关性 × 艾宾浩斯时近度 × IDF 校正实体图核心度」打分，高价值消息逐字保留为记忆卡。效果：同样 1.1 倍 token，长对话精确事实恢复从 **0/20 提到 17.5/20**；每个组件都过了消融实验，真 LLM 闭环里压缩后问答准确率也有完整账本。"

## 二、2 分钟展位讲解流程

1. **痛点演示（30 秒）**：跑 `pnpm benchmark:demo`——一条 80 轮生信对话，20 条精确事实被上游全部压进摘要；问"TP53 的突变频率是多少"，摘要答不出。
2. **机制（30 秒）**：白板/海报上画公式 `S(m) = 0.7·sim + 0.15·time + 0.15·IDF-PageRank`，三句话讲三个分量：语义对准用户当前请求；时近度用艾宾浩斯衰减；实体图找"被反复讨论的核心实体"。强调中文处理：**免分词 bigram + 高频功能词剪枝 + IDF 校正**。
3. **证据（40 秒）**：海报数字区——主基准表 + 消融表 + 真 LLM 问答准确率。每指一个数说一句"怎么来的、怎么复现"。
4. **工程素养收尾（20 秒）**："所有改动有 no-regression 守护：不启用 scorePolicy 时与上游基线**逐字节一致**；全仓 477 个测试 0 失败；打分开销毫秒级、相比一次 LLM 摘要调用占比 5–15%。"

## 三、三大证据卡（对应评分维度）

### 卡 1 · 技术深度
- 评分式保留公式三项可插拔（`scorePolicy` 注入，不破坏上游字节级兼容）
- **双语实体抽取**：ASCII 大写驼峰 + 中文滑动 bigram（免分词），文档频率剪枝功能词
- **消融驱动的两轮修复**（有完整过程可讲）：
  1. 消融发现原始 PageRank 单独使用 0 分 → 机制分析：共现枢纽是重复噪音 → **IDF 校正** `log(1+M/df)` → 中文 rank 项 0 → 3.5
  2. 消融发现旧权重让 time/rank 稀释主力 sim 项 → 18 配置网格搜索重锚 → 新默认 **6/6 组全第一**
- 消融表（中位数，facts/20）：

| 变体 | EN N=160 | ZH N=160 |
| --- | ---: | ---: |
| sim only | 16 | 8 |
| time only | 2 | 2 |
| rank only（原始） | 0 | 0 |
| rank only（+IDF） | 0 | 1.5 |
| full 旧默认 0.4/0.35/0.25 | 10.5 | 6 |
| **full 新默认 0.7/0.15/0.15+IDF** | **17.5** | **10** |

### 卡 2 · 效率
- 压缩后 token：Hippo ≈ 上游的 **1.11–1.22×**（换回全部逐字事实）
- 打分延迟（本地计算，无网络）：EN 15–60ms，ZH 185–565ms（N=40→160）；对比真 LLM 摘要调用秒级，占比 ≈5–15%，且压缩是低频事件
- 真 LLM 账本（`benchmark:real-llm`）：摘要调用 token、评审 token、墙钟时间全部落 JSON——"我们不只说省 token，我们把每次压缩的 token 去哪了记了账"
- 记忆卡未来可跨轮复用（读取侧索引在路线图），一次压缩的成本摊薄到多轮

### 卡 3 · Agent 更聪明
- 主基准（fake summarizer，结构对比）：精确事实恢复 **0/20 → 8、9、17.5**（N=40/80/160）
- 真 LLM 闭环（DeepSeek-V4-Flash 真摘要 + 同模型评审，压缩后只能靠上下文答题）：

| 场景 | 上游 | Hippo | 代价 |
| --- | ---: | ---: | ---: |
| EN N=160 问答准确率 | 12.5% | **87.5%** | token +16% |
| ZH N=160 问答准确率 | 0% | **81.3%** | token +24% |
| EN N=80 | 68.8% | 68.8%（打平，如实报） | — |

  一句话：**短对话强摘要能兜住，长对话纯有损摘要必崩，Hippo 稳住。**
- 中文同等有效：`generateZhTranscript` 中文对话上 Hippo > 上游（有专项测试）

## 五、预答辩 Q&A（评委可能怎么问）

**Q1：消融显示 time/rank 单独都很弱，为什么还留着？**
> 消融的口径是"单独使用"。合成分布事实偏前、query 在尾，time 天然反相关——这是分布特性不是组件缺陷。组合上新默认 6/6 组第一；且无 query 的最坏场景（BM25 失效）里 IDF-rank 是唯一还有信号的项。权重经网格搜索重锚而不是拍脑袋。

**Q2：中文为什么不用分词器？**
> 分词器是重依赖且领域词表要维护。滑动 bigram 免分词、零依赖、确定性，配合文档频率剪枝去功能词、IDF 校正去枢纽效应，在基准上已过专项测试。代价是实体数膨胀（延迟 185–565ms），仍远低于一次 LLM 调用，且有截断参数可调。

**Q3：合成基准会不会过拟合？**
> 权重是在该分布上网格搜索的，我们不回避这点（README 诚实说明里写了）。但两轮机制修复（IDF 校正、剪枝）是分布无关的原理性修正；且双语、三规模、10 seeds、确定性守护 + 真 LLM 闭环三套证据互相独立。

**Q4：真 LLM 摘要也很强，上游还会是 0 分吗？**
> 真 LLM 闭环里上游确实不是 0 分：短对话强摘要模型能兜住（EN N=80 打平 68.8%），它甚至会自发把检查点抄进摘要。但压力一大（N=160）就崩——EN 12.5%、ZH 0%，Hippo 同场景 87.5%/81.3%。「摘要质量」救不了「有损机制」，这是机制差距不是模型差距。

**Q5：为什么不直接换更强的摘要模型？**
> 换模型改变的是"有损压缩的质量上限"，不改变"有损"本身；且更强模型更贵。Hippo 是正交改进：任何摘要模型之上都能叠加，包括端侧小模型（赛事 100 元端侧额度正好够 BGE embedding）。

**Q6：延迟 / 成本？**
> 打分毫秒级本地计算（卡 2 有数）；真 LLM 闭环全套评测（32 次摘要 + 256 道问答评审）共 65.5 万 tokens，全程走 flash 档，成本不到 1 元人民币——有完整的 token 账本可查。
