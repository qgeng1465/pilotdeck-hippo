PilotDeck-Hippo：压缩会丢事实，Hippo 把一部分内容移出有损路径

PilotDeck 在上下文吃紧时会压缩对话：保留最近一段（tail）的原文，把更早的历史摘要成一段文字。 摘要保得住大意，但会丢掉低频的精确事实——基因名、频率数字、文件路径、检查点、决策记录， 而这些正是 Agent 之后要逐字复述的东西。Hippo 不打算做一个更好的摘要器， 而是在 CompactionEngine 上加一条可开关的保留路径：压缩前对即将被摘要的消息逐条打分， 按一个固定的 token 预算挑出得分最高的若干条，让它们的原文和摘要一起进入压缩后的上下文。

同一份输入、同一次压缩：上游压缩后 20 条早期事实里 0 条逐字还在，Hippo 4–16 条还在 （范围来自 holdout 的四个格子，见 §2.2）；代价是压缩后的 token 多付 1.11–1.20×。

怎么做到的：保留不是重写摘要——是在压缩前把一小批消息从“将被摘要掉”的集合里拿走， 让它们的原文直接进入压缩后的上下文；预算硬上限 = tail 预算的 20%（下限 256 tokens）。 全过程见 §1.1，两条路的逐条对照见 §1.2，基准数字见 §2。

1 — 核心机制

S(m) = 0.85 × sim(q, m)          # 与当前待办请求的语义相关度（默认 BM25，可选本地 embedding）
     + 0.15 × position_decay(m)  # 越靠近当前越可能相关
     + 0.00 × idf_pagerank(m)    # 实体共现图核心度；默认权重 0，公式项与配置项保留

retentionBudgetTokens = max(256, floor(tailTokenBudget × 0.2))
const engine = new CompactionEngine({
  model,
  // 不传 scorePolicy 时，引擎走纯上游摘要路径
  scorePolicy: buildEbbinghausPageRankPolicy({ wSim: 0.85, wTime: 0.15, wRank: 0 }),
});

关键不在打分公式，在路径。摘要是有损的，保留块不是：Hippo 把少量消息从"将被摘要掉"的集合里直接拿走， 逐字放回压缩后的上下文，因此这部分内容不受摘要模型能力波动影响。打分公式只决定"拿哪几条"。

  • 预算是硬的：保留块最多花掉 tail 预算的 20%（RETENTION_BUDGET_RATIO = 0.2， src/context/compaction/CompactionEngine.ts），下限 256 tokens。对话再长，压缩后的上下文也不会因为"想多记一点"而失控。
  • 输出是原文：被保留的消息逐字进入上下文，不是转述。
  • 失败即退让：打分抛错、embedding 加载超时或模型缺失，一律退回纯上游摘要路径（pickRetained 外层 try/catch），不阻塞对话。

一处机制细节：压缩不一定由新的用户请求触发（一条超长工具输出也能撑爆预算）。此时 tail 里没有用户消息， 相似度项会归零。引擎现在回退到全对话中最近的一条真实用户请求，而不是用空串打分； 撤销这条回退会让 tests/context/hippo-retention.spec.ts 里的回归用例确定性失败。

1.1 压缩全过程：一条消息是怎么被留下来或折进摘要的

一次压缩，逐步走：Hippo 到底多做了什么

40 轮合成对话共 81 条消息（含 8 条注入的精确事实），跑一次真实的压缩。上游把「摘要桶」里的消息全部换成摘要文本；Hippo 在换之前先给桶里每条消息打一个分，把分数最高、且能塞进硬预算的几条原样留在上下文里。下面五步就是这一次压缩的逐步回放。

页面上的每个数字都来自 sections/flow.json——它由 benchmarks/demo/exportFlow.ts 调用本仓库真实的 CompactionEngine 与 EbbinghausPageRankPolicy 生成，用假模型出摘要（固定字符串），不联网、不用 API key、不调真 LLM。同一 seed 重跑两次输出逐字节一致。这不是一次实时模型调用，是一次可离线复现的固定种子回放。

1压缩前 81 条消息 · 4200 tokens

进上下文前先看原样：40 个 user/assistant 来回，加最后那条待回答的请求（第 81 条）。最后一条请求是打分用的查询 q。

静态摘要（JS 未运行 / flow.json 未加载）
  • 81 条消息 = 40 组 user/assistant 对话 + 1 条待回答的请求；压缩前共 4200 tokens。
  • 其中 8 条 user 消息带注入事实（FACT1…FACT8），分别在第 1、7、15、23、31、37、45、53 条。
  • 第 81 条 Answer the TCGA-LIHC n/frequency/statistic questions… 是这次压缩要服务的请求，也是打分用的查询。
  • 此时还没有任何消息被摘要，也没有任何消息被逐字保留。
2进入摘要桶的候选 60 条候选 · 尾部 21 条不动

压缩先把对话切成「尾部」和「前缀」：尾部按 token 预算逐字保留，前缀整体进摘要桶——桶里的消息原话就没了。这次尾部 = 最后 21 条（第 61–81 条，含待回答的请求），不参与打分；剩下 60 条是候选，也就是这张图里被标黄的那些。

静态摘要
  • 尾部预算 = floor(4200 × 0.18) = 756 tokens，实际取到最后 21 条逐字保留，不参与打分。
  • 前缀 60 条进入摘要桶，成为候选——上游在这里就把它们全部换成摘要文本。
  • 8 条 FACT 消息全部落在候选里（第 1…53 条），所以上游压缩后一条原文都留不下。
  • 待回答的请求在尾部，因此不会被摘要掉。
3打分：本地算，不花第二次模型调用 60 条候选 · 权重 0.85 / 0.15 / 0.00

Hippo 给每条候选单独打分：S(m) = 0.85·sim(q,m) + 0.15·position_decay(m) + 0.00·idf_pagerank(m)。sim 是查询与消息文本的 BM25 词面相似度，position_decay 是按「越新越靠前」的指数衰减，idf_pagerank 是实体图中心度（本版权重为 0，只作显示）。三项都在进程内算完：没有第二次 LLM 调用，没有网络。下面按分数从高到低排。

静态摘要
  • 公式：S = 0.85·sim + 0.15·position_decay + 0.00·idf_pagerank，查询是最后那条请求。
  • 分数最高的 8 条恰好就是 8 条 FACT 消息：0.8986 / 0.8817 / 0.8669 / 0.8571 / 0.8455 / 0.8353 / 0.8264 / 0.8205。
  • 其余 52 条候选最高只有 0.7164，最低 0.0581——差距主要来自 sim（FACT 消息 sim≈0.9004，噪声消息约 0.67 及以下）。
  • 全部计算在本地完成：BM25 词频统计 + 指数位置衰减 + 实体图 PageRank，不调用模型。
4预算截断 硬预算 256 tokens

逐字保留是有硬预算的：max(256, floor(756 × 0.2)) = 256 tokens。按分数从高到低往下取，取到装不下为止。注意实现细节：装不下的一条会被跳过，然后继续往下试更小的消息——不是一撞到上限就停。这次 6 条刚好用掉 226/256，第 7、8 名（就是 FACT1、FACT2）无论放哪都超预算，于是留在摘要桶里。

静态摘要
  • 预算 max(256, floor(756 × 0.2)) = 256 tokens（756 是尾部预算，0.2 是保留比例，256 是下限）。
  • 按分数顺序取：36 + 37 + 40 + 38 + 38 + 37 = 226 tokens，共 6 条，落在上限 256 以内。
  • 第 7 条（FACT1，37 tokens）会让累计到 263，第 8 条（FACT2，39 tokens）会到 265，都超过 256，所以跳过。
  • 60 条候选里 6 条被逐字保留，其余 54 条留在摘要桶里（跳过而非截断，剩余 30 tokens 装不下任何一条）。
5结果：两栏对比 上游 1253 tokens · Hippo 1479 tokens

左边是上游压缩后的上下文，右边是 Hippo 的。两栏的摘要文本完全一样（同一次假模型输出），差别只在右栏多了 6 条逐字保留的原文——就是 FACT3…FACT8。上游那条请求现在只能问摘要里的东西，Hippo 还能查到原文。

静态摘要
  • 上游压缩后 1253 tokens，0/8 条 FACT 原文存活；Hippo 压缩后 1479 tokens（多出的 226 正好是保留的原文），6/8 条 FACT 存活。
  • 存活的是第 15、23、31、37、45、53 条消息，即 FACT3…FACT8；FACT1、FACT2 因为排在第 7、8 名、装不进 256 token 预算而只留在摘要里。
  • 两栏的摘要文本相同（都是固定的假模型输出），差别只是右栏多了 6 条原文块。
  • Hippo 侧的边界标记里写着 messagesSummarized="54"：被逐字保留的 6 条是从摘要桶里拿掉的，改为原样回放，送去写摘要的是剩下的 54 条——与上一步的截断结果一致（上游侧没有保留机制，标记里是完整的 60）。

2.5 长程任务：同一个任务跨多次压缩

压缩不是一次性的。上下文逼近预算上限就自动触发一次压缩，所以开得久的任务会跨过多次压缩边界。上游的路径是 逐次重写摘要——老的摘要在下一轮被再摘要一次，低频细节每一轮都会再掉一些；Hippo 在每次压缩前把得分最高的 一小段原文钉住、不让它进入有损路径，所以任务跑得越久，两侧的差别越集中在「早期那些精确细节还在不在」。

场景（同一个仍在进行的任务）上游Hippo来源

预算宽裕（8,000 tok） 16/1616/16 real-llm-topic-switch-2026-09-11T12-29-27-528Z.json

逐格数字与口径见 2.4（同一批 JSON）。两行合起来才是完整的口径： 保留的价值在摘要器扛不住预算时显现；预算宽裕时上游的摘要本身就装得下这些细节，两侧测不出差异。

跨多次压缩的结构性基准（corepack pnpm benchmark:long-horizon）：同一个仍在进行的任务连续压缩 3 次，每一轮以上一轮的实际输出作为输入（不是重新模拟），事实持续注入；下表是压缩结束后逐字仍在的 事实条数，80 个 seed 的均值（seed 20261021–20261100）。

保留不是记忆。最旧那 5 条两侧最终都几乎归零（上游 0.00 / Hippo 0.00）：一个事实跨过几轮压缩之后，再旧也一样会掉—— Hippo 没有解决这件事，也不声称解决。

跨轮次这次新加的一条机制：被上一次压缩逐字保留过的消息会带 metadata.hippoRetained: true 标记， 下一次压缩时给这批消息一小块封顶预算（保留预算的 25%，CARRYOVER_BUDGET_SHARE， src/context/compaction/retention/CarryOver.ts），让它们优先占位。这不是加权—— 候选排序完全不变，所以挤不掉当前问题真正需要的消息。80 seed 配对：中间那批 1.36 → 1.80 （27 胜 / 53 平 / 0 负），合计 6.38 → 6.78（25 / 54 / 1），最新那批 5.00 → 4.97 （80 个 seed 里 2 个各少 1 条）。它没有保住最旧那批（0.01 → 0.00）——那本来就是这个改动的目标， 实测没做到，如实写在这里。PILOTDECK_CARRYOVER=off 一行关掉。

边界（如实说明）。如果问的是被放弃的旧话题，Hippo 一样答不出来：保留是按当前请求的相关性打分的， 在压缩发生的那一刻不可能预知你几轮之后要问什么。这条不是推断——我们在真机 UI 上把同一段对话跑了两遍 （唯一差别是 agent.compaction.retention 开关），四轮无关话题之后回头问第一轮里的一个编号， 两侧都没答出来；这与 README §4.6/§4.7 记录的「旧话题优势在措辞去相关后归零」一致。 所以本节主张的只有上面第一行：同一个仍在进行的任务，跨多次压缩之后早期精确细节仍可逐字复述。 那段录屏因此没有作为证据放上来——它测不出差别，放上来只是充数。

3 — 验证方式

  • 合成基准：pnpm benchmark，生信对话把 20 条精确事实分散在前 75%，tail 提问要求逐字复述； 每格 10 cases，全部 deterministic=true。上游臂用不生成 FACT 文本的假摘要器，做结构性对照。
  • 留出集：pnpm benchmark:holdout。调参与消融只用 ≤ 20260920 的 seed； 留出集固定取 20260921–30 共 10 个 seed，从未参与任何选择（权重、IDF 开关、PageRank 迭代数）。 统计上每个 seed 与自己配对，报 per-seed 差值、胜/平/负与双侧精确符号检验 p。
  • 独立抽检：换一批全新 seed（holdout 用 20261001–10、精度用 20261011–13）复跑， seed 与 tune/ablation/留出集全部不相交；脚本支持 PILOTDECK_HOLDOUT_SEED_BASE 覆盖，任何人都能自己换 seed 重跑。
  • 真 LLM 闭环：pnpm benchmark:real-llm / pnpm benchmark:real-llm-topic-switch， 摘要器与评审员均为 DeepSeek-V4-Flash，每格 16 题 × 2 seeds，两轮换不同的摘要输出预算。
  • 无回归门：pnpm benchmark:no-regression —— 不传 scorePolicy 时， 引擎输出必须与上游基线 85be774 逐字节一致（golden fixture benchmarks/baseline-85be774.json）。 本页实测输出：NO-REGRESSION OK: scorePolicy=undefined output matches upstream 85be774 baseline.
  • 原始数据随仓库提交：上面每个数字都对应 benchmarks/results/*.json 里的一个字段， README §4.8 给了逐数字 → JSON 行的对账索引。
这些数字全部是我方自跑，不是第三方评审。抽检记录（docs/independent-spotcheck.md）也明确这么标注： 它回答的只是"换一批从没用过的 seed，旗舰数字还在不在"，不能替代独立评审或人工抽检。 真 LLM 闭环里摘要器与 judge 是同一个模型，这项偏差没有被消除。

5 — 代码质量 / 工程

  • 测试与类型检查现在都是绿的：根套件 pnpm test 520 项 / 518 通过 / 0 失败 / 2 skipped； UI 侧 npx vitest run 118 个文件 / 922 个用例 / 0 失败；ui 的 tsc --noEmit 退出码 0（基线 101 文件 / 511 处报错）。修的都是测试侧与环境侧问题，没有靠 @ts-ignore、as any 或放宽断言换来。
  • CI（.github/workflows/ci.yml）：typecheck → 无回归门 → 根套件；测试步骤只在 # fail 计数非零时失败，不放宽对 flake 的容忍。另有 docker-build.yml。 保留徽章另有专项测试：根套件 tests/context/retention-reporting.spec.ts， UI 侧 useChatMessages.retention.test.ts（14 例）与 MessageComponent.retention-badge.test.tsx（6 例，做过变异验证：把徽章渲染条件改成恒假后 4/6 正例失败）。
  • 无回归守护：引擎层 scorePolicy 缺省 = 上游路径，golden fixture 锁定上游 85be774 的行为， pnpm benchmark:no-regression 逐字节比对；App 层本 fork 默认 retention: hippo， off 一键关回上游。Hippo 是纯增量：不传策略时输出与上游完全一致。
  • 上游缺陷一 · 被 unref() 掉的超时定时器：本应用来 settle 一个被 await 的 promise 的定时器被 unref()，事件循环先排空，调用方拿到永不 settle 的 promise 而不是超时错误。 三处站点（src/network/fetch.ts、src/task/runtime/BackgroundTaskRuntime.ts 的 wait()、 src/model/streaming/streamModel.ts 的 withIdleTimeout()），每处都配了一个修复前必然失败的测试 （修复后 7/7、6/6、6/6）。其余站点是有意不阻止进程退出，未动。
  • 上游缺陷二 · 分词器二次退化：src/context/budget/tokenizer.ts 在长重复串上退化为 O(n²) （CPU profile 显示 96% 时间在 js-tiktoken 的 bytePairMerge）； countTokens 换成同一套贪心合并的堆实现后，8,000 字符 8,998.9 ms → 9.1 ms。 数据见 benchmarks/results/tokenizer-scaling-2026-09-11T13-06-44-566Z.json； tests/context/tokenizer-equivalence.spec.ts 用 906 次比对（900 随机 + 6 固定边界）验证等价性，0 失配。
  • 上游缺陷三 · "最新事务"的排序键混了逻辑时间与文件 mtime： src/web/server/replaceLastTurn.ts 原本写 Math.max(preparedAt, backupMtime, journalMtime)， 而本机 mtime 粒度是 1 ms，两个事务落在同一毫秒就并列，并列由 readdirSync 的任意顺序决定， 启动恢复会挑错事务。改成 preparedAt 可解析时由它单独决定，mtime 只兜底； 新增的测试用 utimes 把旧事务 mtime 推到未来 60 秒，不依赖时序，改回旧代码确定性失败（修复后 16/16）。

6 — 已知限制

  • 收益是对当前任务保真，不是"记住被放弃的旧话题"。旧话题那一列的优势经诊断是 harness 句式共享造成的假象， 换成 decorrelated 措辞后归零（§4.6/§4.7）；对外不应说"Hippo 保住了旧话题"。
  • 评测主要是合成转录、模板化事实，上游 0/20 是假摘要器的结构性对照，不是真实摘要能力上限； 真 LLM 闭环每格只有 16 题、2 个 seed，且摘要器与 judge 同模型，只声明方向。
  • Hippo 会增加压缩后 token（结构性基准约 1.11–1.20×，真 LLM 记录约 +5–24%，视轮次与格子）。 展示时应同时给准确率与成本，不能只报准确率。
  • ui/ 的 tsc --noEmit 基线是 101 个文件 / 511 处报错（lucide-react 的 .d.ts 解析到根提升的 @types/react 19，而 ui 自己跑在 18 上），现已修到退出码 0； vite build 退出码 0（40.4 s）。
